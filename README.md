# Codex Monitor Wrapper v0.3.2

A lightweight Windows terminal wrapper for the **official OpenAI Codex CLI**.

It does not replace, patch, or rebuild Codex. `codexm` launches your existing `codex` inside a ConPTY pseudo-terminal and reserves a small dashboard at the bottom of the same terminal.

```text
╭─ CODEX MONITOR ─────────────────────────────────────────────────────────────────────────────────────╮
│ gpt-5.6-luna · medium · my-project · main +3 · ● IDLE waiting input · SESSION 12m · TURN 8 · DUR 7.4s · UPD 2s │
│ 5h waiting… · Week ━━━━━━━━━━━━━━━──── 82% left ↻ 6d07h │ STATE IDLE wait · THINK reason · TOOL exec · APPR approve · ERR fail │
│ IN 4.07M · CACHE 3.96M 97% · OUT 5.9K · RSN 644 · TURN IO 2.1K in · 25 out · CTX ━━━━──────── 79K/258K 27% used│
╰──────────────────────────────────────────────────────────────────────────────────────────────────────╯
```

## What it does

- Runs the official Codex CLI unchanged.
- Keeps the monitor in the same terminal window; no separate GUI or tray app.
- Reads Codex's local rollout/session JSONL files under `%CODEX_HOME%\sessions` or `%USERPROFILE%\.codex\sessions`.
- Updates the dashboard continuously while Codex runs.
- Automatically follows the current Codex session instead of staying attached to an older rollout.
- Makes **no additional model/API requests** for monitoring.
- Leaves `codex` untouched; use `codexm` when you want the dashboard and `codex` when you do not.

## Dashboard metrics

| Item | Meaning |
| --- | --- |
| `gpt-5.6-luna` | Model currently observed for this Codex session. |
| `medium` | Reasoning effort selected for the current model/session. |
| `my-project` | Current working directory/project name. |
| `main` | Current Git branch. |
| `+3` | Git working tree is dirty; the number is the count of changed/untracked paths reported by `git status --porcelain`. Hidden when clean. |
| `IDLE` | Codex is waiting for the next user action. |
| `THINKING` | A Codex turn is active and the model is processing. |
| `TOOL` | Codex is currently running a command/tool, MCP call, web search, patch operation, or similar tool lifecycle event. |
| `APPROVAL` | Codex is waiting for an interactive approval/permission/user-input request. |
| `ERROR` | The latest active lifecycle state is an error. It normally clears when the turn completes or a new turn starts. |
| `SESSION` | Time since `codexm` launched the current Codex process. |
| `TURN` | Number of turn contexts seen in the current rollout/session. |
| `DUR 7.4s` | Duration of the most recently completed Codex turn, measured from Codex `task_started/turn_started` to `task_complete/turn_complete`. `--` means no completed timed turn has been observed yet. |
| `UPD 2s` | Age of the newest Codex event seen in the active rollout. This is **not** the dashboard refresh interval. |
| `CMP 2` | Number of context compaction events observed. Hidden when zero. |
| `RETRY 1` | Number of model stream retry/disconnect events observed. Hidden when zero. |
| `ERR 1` | Number of error events observed in the current session. Hidden when zero. |
| `5h` | Rolling 5-hour quota window when Codex supplies one. If OpenAI temporarily does not expose this window, the monitor shows `waiting…` instead of inventing a value. |
| `Week` | Rolling weekly quota window. |
| `82% left` | Percentage of that quota window still available. |
| `↻ 6d07h` | Countdown until the quota window resets, based on Codex's reported reset timestamp. |
| `IN` | Total input tokens reported for the session. |
| `CACHE` | Cached input tokens. The percentage beside it is `cached input / input`. A high percentage generally means more of the input was served from cache. |
| `OUT` | Total output tokens generated by the model. |
| `RSN` | **Reasoning output tokens** reported by Codex: tokens used by the model's internal reasoning process. This is separate from visible output tokens. Some model/response combinations may report `0`. |
| `TURN IO 2.1K in · 25 out` | Input/output tokens from the latest token-usage snapshot (`last_token_usage`). Units are written explicitly so the two values cannot be confused. |
| `CTX 79K/258K` | Current context tokens reported for the latest turn versus the model context-window size. |
| `27% used` | Effective context usage using the same 12K-token baseline concept Codex uses for its context-remaining calculation. This can differ from the raw `79K / 258K` ratio because fixed prompts/tools/baseline tokens are discounted. |


## State legend

On wide terminals, the unused space on the quota row becomes a compact state cheat-sheet:

```text
STATE IDLE wait · THINK reason · TOOL exec · APPR approve · ERR fail
```

The legend is intentionally short and dim so it does not compete with live metrics. It only appears when the terminal is wide enough; narrower windows automatically hide it rather than squeezing quota/token information.

- `IDLE`: Codex is waiting for input.
- `THINK`: the model is reasoning/processing an active turn.
- `TOOL`: a command, tool, MCP call, web search, patch, or similar tool operation is active.
- `APPR`: Codex is waiting for approval, permission, or interactive input.
- `ERR`: the latest active lifecycle state is an error.

The live state in the header also includes a short description on medium/wide terminals, for example `● IDLE waiting input` or `◆ TOOL executing`.

## Color meaning

Quota bars are colored by **remaining quota**:

- More than 60% left: green.
- 20% to 60% left: orange.
- Below 20% left: red.

Context is intentionally different because it represents **usage**, not remaining quota:

- Used part of the context bar: orange.
- At 80% used or more: red.
- Unused portion: dim gray.

Other metric colors are only visual grouping:

- `CACHE`: cyan.
- `OUT`: blue.
- `RSN`: purple.
- Last-turn values: gold/yellow.
- Labels, reset countdowns, and secondary timing information: dim/gray.

## Refresh behavior

The wrapper is designed to feel live without repeatedly rereading large session files unnecessarily:

- Dashboard repaint: about every **250 ms**.
- Search for a newly created/current rollout: about every **400 ms**.
- Check the active rollout for changes: about every **100 ms**.
- The rollout file is only reread when its modification time or file size actually changes.
- Git branch/dirty state: refreshed about every **3 seconds**.

Token/quota/state values therefore normally appear shortly after Codex writes the corresponding event locally. No network polling is performed by the monitor.

## Installation

Requirements:

- Windows 10/11 with ConPTY support.
- Node.js 20-26.
- Official Codex CLI already installed and working.
- `@homebridge/node-pty-prebuilt-multiarch` installed by the wrapper installer.

Install the wrapper, then run:

```powershell
codexm
```

The official CLI remains unchanged:

```powershell
codex
```

Diagnostic check:

```powershell
codexm --doctor
```

All normal Codex arguments are passed through, for example:

```powershell
codexm resume
codexm --help
```

## Data and privacy

The monitor reads local Codex session data and Git state from the current workspace. It does not send monitoring telemetry to a separate service and does not make extra model calls to obtain quota/token information.

The local data source includes Codex `token_count` events and lifecycle events such as turn start/completion, tool start/end, approval requests, compaction, stream errors, and errors.

## Notes

### `5h waiting…`

This is intentional when the active/recent Codex data does not contain a distinct 5-hour rate-limit window. The monitor keeps the slot visible so it can populate automatically if/when that window is supplied again.

### `UPD` is old even though the dashboard is moving

`UPD` measures the age of the latest **Codex event**, not the repaint loop. If Codex is idle, `UPD` naturally grows. After a new prompt/response, it should become recent again when Codex writes events.

### Context percentage looks lower than raw tokens/window

The monitor mirrors Codex's effective-window idea by subtracting a 12,000-token baseline before calculating `% used`. This represents fixed prompt/tool overhead that the user cannot directly control.

### Very narrow terminals

The monitor automatically falls back to a compact layout. Wide terminals keep the richer three-line dashboard.

## Uninstall

Removing the wrapper does not modify Codex, login state, or `~/.codex` session data. Use the project's uninstall script or remove the wrapper's global npm link/package as appropriate.

## v0.3.1 display safety

`v0.3.1` reserves a real terminal scroll region above the monitor. Long Codex
responses now scroll inside the Codex area instead of scrolling underneath the
fixed dashboard and being overwritten by the next monitor repaint.

The dashboard still truncates its own unusually long metadata (for example a
very long project or branch name), but ANSI colours are preserved when that
happens.

## v0.3.2 state legend

Wide terminals now use spare horizontal space for a compact state legend instead of leaving the right side empty. The current live state also carries a short human-readable description. The legend disappears automatically when there is not enough width, so the monitor never sacrifices the primary quota/token metrics just to show help text.

## v0.3.3 state guide

On wide terminals, the state legend is now isolated in the right-hand corner
instead of being mixed into the quota row.

The current state is the only legend item shown in a bright semantic color.
All other states stay dim so the legend acts as a reference without competing
with the live metrics.

The header also spells out the active state in plain language:

- `IDLE` — waiting for input
- `THINKING` — reasoning
- `TOOL` — running a tool or command
- `APPROVAL` — waiting for approval
- `ERROR` — the latest active state is an error

On narrower terminals the right-side guide is hidden automatically; the active
state and its explanation remain visible in the header.

## v0.3.4 lifecycle fix

This release changes the activity indicator from a "latest event wins" model to
a small lifecycle state machine.

- `TOOL` stays active while at least one tracked tool call is still open.
- Tool calls are detected from both Codex lifecycle events (`exec_command_*`,
  MCP, web search, patch/image events) and persisted response items such as
  `function_call` / `function_call_output`.
- Concurrent calls are tracked by `call_id`, so one tool finishing does not
  incorrectly clear another active tool.
- `APPROVAL` remains active until execution begins or the turn ends.
- `ERROR` is cleared when a new turn starts; terminal turn errors can also set it.
- `LAST 7.4s` was renamed to `DUR 7.4s`.
- `LAST 2.1K/25` was renamed to `TURN IO 2.1K in · 25 out`.

The right-side state guide still highlights only the current state. The active
symbol now also matches the state: `●`, `◆`, `!`, or `×`.

## v0.3.5 demo mode

`codexm --demo` is handled by the wrapper itself and is **not** forwarded to
the official Codex CLI.

It cycles through all monitor states every 2 seconds:

```text
IDLE -> THINKING -> TOOL -> APPROVAL -> ERROR
```

Press `Ctrl+C` to leave demo mode.

You can also hold one state indefinitely:

```powershell
codexm --demo-state IDLE
codexm --demo-state THINKING
codexm --demo-state TOOL
codexm --demo-state APPROVAL
codexm --demo-state ERROR
```

Demo mode uses synthetic values only. It is intended to test colors, labels,
layout, and the active-state legend. It does not test whether a live Codex
session emitted the corresponding lifecycle signal.

## v0.3.6 consolidated live-state fix

This package consolidates the current monitor files so you do not have to
combine earlier patches manually.

### State sources

The dashboard now intentionally combines two data sources:

1. **Rollout/session JSONL** for durable data such as tokens, quota, turn
   lifecycle, and persisted tool calls.
2. **Live PTY output** for transient UI states that Codex does not persist to
   rollout history.

This distinction matters because current Codex rollout policy does not persist
approval-request events such as command approval, permission approval, or
apply-patch approval. The wrapper therefore watches the visible Codex UI for
official approval prompts such as:

```text
Would you like to run the following command?
Would you like to grant these permissions?
Would you like to make the following edits?
Do you want to approve network access to ...
... needs your approval.
```

When one appears, the monitor overrides the durable tool state with:

```text
! APPROVAL waiting for approval
```

After you confirm/deny/cancel the prompt, the monitor falls back to the
underlying state (`TOOL`, `THINKING`, or `IDLE`).

### Error detection

Codex renders terminal error history cells with a red square prefix:

```text
■ <error message>
```

The wrapper watches that PTY form conservatively and shows `ERROR` for a short
period. Generic command output containing the word "error" does **not** by
itself trigger the dashboard error state.

### Priority

When several signals overlap, the dashboard uses:

```text
ERROR > APPROVAL > TOOL > THINKING > IDLE
```

### Current labels

- `DUR 16s` — duration of the most recently completed turn.
- `TURN IO 49.5K in · 5 out` — input/output tokens for the latest usage
  snapshot, with explicit units.
- `--demo` — cycles through all five visual states without launching Codex.
- `--demo-state APPROVAL` (or any other state) — holds one state for visual
  inspection.

### Live-state limitation

PTY detection depends on the visible wording/icons produced by Codex. If a
future Codex release changes those approval titles or its error-cell prefix,
the wrapper patterns may need a small update. Token/quota parsing remains
independent of those UI strings.

## v0.3.7 transient-state and demo fixes

### Approval resurrection fix

A previous PTY detector kept a short tail so it could recognize an approval
sentence split across two terminal writes. The detector accidentally allowed a
complete approval sentence that existed only in the *old* tail to fire again.

That caused this incorrect sequence:

```text
APPROVAL -> ERROR -> APPROVAL
```

`v0.3.7` only accepts a PTY match when the match reaches into the newly received
chunk. A phrase may still begin in the retained tail and finish in the new
chunk, so split approval titles continue to work.

The approval latch is also cleared when Codex displays cancellation,
interruption, execution, or a terminal error.

### Demo fix

`codexm --demo` previously failed with:

```text
ReferenceError: writeRaw is not defined
```

The terminal writer is now top-level and shared by normal mode and demo mode.

These commands are available again:

```powershell
codexm --demo
codexm --demo-state IDLE
codexm --demo-state THINKING
codexm --demo-state TOOL
codexm --demo-state APPROVAL
codexm --demo-state ERROR
```
